多 Agent 协作：选品 + 文案 + 设计流水线

一个 Agent 是员工，一群 Agent 是部门。这一节看三个 Agent 怎么接力完成一次完整的上新——以及一个“包工头”角色为什么必不可少。

动画概念8 分钟
为什么要拆成多个 Agent

一个“全能 Agent”负责整个上新？听起来美，跑起来糟：提示词塞了选品规则 + 文案风格 + 设计规范几千字，样样通样样松，一出问题还找不到是哪个“人格”犯的错。

拆开的道理和开店一样：专业的人干专业的事。选品 Agent 只懂选品逻辑，提示词短而精；文案 Agent 只钻研文案；设计 Agent 只管出图。每个都好调、好测、好追责。代价是需要一个调度者（Orchestrator）——包工头，负责派活、验收、传话。

动画演示 · 一次上新的接力赛
任务：秋季新款针织衫上新
多 Agent 协作的三条军规
  • 串行还是并行，看依赖：文案必须等选品定款（串行）；但主图和详情图可以同时出（并行）。依赖关系画清楚，效率翻倍；画不清，全是返工。
  • 交接必须结构化：Agent 之间传的不是“一段话”，是 JSON 式的结构化数据（款号、卖点、禁忌、风格要求）——还记得 2-3 节吗？给程序读的用 JSON，多 Agent 场景就是给程序读。
  • 冲突由包工头裁决：文案 Agent 想打“慵懒风”，设计 Agent 出了“职场风”——冲突不能靠两个 Agent 互吵解决，调度者拿着品牌规范一票裁决，打回重做。
别急着上多 Agent。单个 Agent 跑顺一个环节，再考虑串联——多 Agent 是放大器：单点 90 分，串起来放大成流水线；单点 60 分，串起来放大成灾难现场。
📌 本节要点
  • 拆 Agent 的理由：专精 > 全能——每个 Agent 提示词短、好调、好追责。
  • 调度者是必需品：派活、验收、裁决冲突，一个不能少。
  • 三条军规：依赖定串并行、交接用结构化数据、冲突包工头裁决。
  • 先单点跑顺再串联：多 Agent 是放大器，不雪中送炭。
