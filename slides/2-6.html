工具调用：让 Agent 会查库存、查物流

AI 自己不会连你的 ERP——它只会“写纸条”，真正跑腿的是系统。看懂这条链路，就懂了 Agent 的“手”是怎么长出来的。

交互动画8 分钟
先破除最大的误会

很多人以为“AI 查了库存”是 AI 亲自钻进你的 ERP 系统翻了一遍。不是的。大模型从头到尾只干一件事：生成文本。它连网都上不了。

真实链路是：AI 生成一条特殊格式的文本（比如 查库存(连衣裙, M码)），外面的系统看到这条文本，替它去查 ERP，把结果“贴回白板”，AI 再看着结果组织人话。AI 是开条的，系统是跑腿的。

工具从哪来？五种常见的“接法”

“接工具”不是玄学，行业里就五种主流接法。你不需要会写，但验收和提需求时要认得它们：

接法连什么一句话说明
平台开放 API店铺订单、商品、库存、物流淘宝/京东/抖店开放平台的官方接口，最正规最稳定，需要申请应用授权
企业系统 APIERP、OMS、WMS、客服系统自家系统开的接口，查库存查物流的主力通道
MCP 接口一切按 MCP 标准封装的工具“AI 界的 USB 口”：工具方封装一次，各家 Agent 即插即用，不用逐个定制对接
数据库直连订单库、商品库、会员库开只读账号直接查库，最快最灵活，但权限必须卡死，得有技术看护
RPA / 低代码连接没有 API 的老系统、后台页面影刀、集简云这类工具模拟人点页面取数，不用开发，代价是慢和脆
运营视角记一句：你的 Agent 能长出几只“手”，取决于你家系统有哪些接口。接 AI 之前先盘家底——店铺有平台 API，ERP 有没有接口，工具生态支不支持 MCP。家底越开放，Agent 越能干。
工具描述：成功率的隐形决定者

同一个“查库存”功能，给 AI 的工具说明书写得好不好，调用成功率能差出 3 倍：

❌ 坏描述
名称：query
功能：查询
参数：input

AI 看到这东西一脸懵：查什么？参数传商品名还是货号？M 码写成“M”还是“M码”？只能靠猜——猜错就是查无结果。
✅ 好描述
名称：check_inventory
功能：查询指定商品的实时库存
参数：sku_name（商品全称，如“法式碎花连衣裙”）、size（尺码，取值 S/M/L/XL）
返回：库存数量 + 预计补货日期

名称说人话、参数有取值范围、返回字段写明白——AI 照单抓药，一调一个准。
给电商团队的三个落地建议
  • 第一批工具只上“只读”的：查订单、查库存、查物流——查错了没损失。写操作（建单、退款）等只读的跑稳了再上，而且要加人工确认。
  • 工具说明书当员工手册写：名称说人话、参数给取值范围、附一个调用示例——你带实习生怎么写 SOP，就怎么写工具描述。
  • 失败要有“人话”返回：查不到时别让系统返回“null”，返回“该商品 M 码缺货，预计 8 月 12 日补货”——AI 拿到人话，才能对客人说出人话。
📌 本节要点
  • AI 开条，系统跑腿：模型只生成指令文本，真正的查询是外围系统干的。
  • 四步链路：输出指令 → 解析执行 → 结果注回白板 → 组织人话回复。
  • 五种接法：平台 API、企业系统 API、MCP、数据库直连、RPA/低代码——家底越开放，Agent 越能干。
  • 工具描述定成败：好描述 vs 坏描述，成功率差 3 倍——当员工手册写。
  • 先只读后写入：第一批工具上查询类，写操作加人工确认闸口。
